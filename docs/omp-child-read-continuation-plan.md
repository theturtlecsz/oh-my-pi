## Decision and source constraints

Do not simply permit a closed `read` pair. `AgentSession.#processAgentEventNow` persists ordinary message_end in its emission-error catch (around 3520–3548). `ExtensionRunner.#runHandlerWithTimeout` reports errors/timeouts through `onError` and can return undefined; successful-looking ToolResult therefore does not prove hooks succeeded. `turn_end` extension handlers run through fire-and-forget session event delivery, independently of the awaited AgentLoop onTurnEnd callback. The existing idle-only `flushBoundTaskCompletion` must not be called while the child model loop is active.

A narrow runtime-produced read-boundary certificate is necessary if this feature must refuse ambiguous/partial hook processing. It must be paired with one processing-start record; otherwise a subsequent response can execute `tool_call` hooks before its assistant is durable (`agent-loop.ts` around 1800–1824), leaving an apparently unchanged read prefix after a crash.

No new AgentLoop API is necessary for the tested provider. R2 uses `openai-completions`: `openai-completions.ts:714` awaits `postOpenAIStream`; `openai-http.ts:91` awaits fetch/headers; `openai-completions.ts:726` awaits `notifyProviderResponse`; only afterward line 787 emits `start`. The retry wrapper buffers/forwards start and does not manufacture a pre-request start. Text-only concurrency/blob wrappers do not add an early start. AgentLoop message_start follows that provider event. Thus a server holding before send_response/end_headers can observe ready without processing-start. Consume through existing awaited `onResponse` BEFORE configured after-provider hooks/SSE/start, not by guessing generic start-event semantics. Other APIs are unsupported for this new slice until their ordering is demonstrated; existing before-answer/completed-result recovery stays unchanged.
